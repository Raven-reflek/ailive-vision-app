# 服务端对接事项(视觉采集 APP → ailive-cloud)

> 写于 2026-10-15。背景:视觉 APP 在"令牌被撤销后仍显示已绑定"的问题上做了**纯客户端修复**(见第 1 节),
> 过程中发现服务端有几处需要配合改动才能彻底解决或做得更好。**本次没有改动任何服务端代码**,这里只做记录,
> 方便后续在 `ailive-cloud`(以及 `ailive-brain/docs/契约/`)里排期。

## 1. 客户端这次做了什么(服务端需要保持不变的约定)

| 场景 | 服务端现有响应 | 客户端行为 |
|---|---|---|
| 令牌被撤销 / "换新手机"批量撤销 | `401` + `{"need_bind": true}`(`server.py` 鉴权闸门) | 清服务器/门店/令牌(**保留标定**),停采集,发通知,跳回绑定页并说明原因 |
| 门店被删除 | `410` + `{"need_bind": true}`(`StoreGone` 处理器) | 同上 |
| 门店被总部停用 / 合作期到期 | `403` + `{"store_disabled": true}` | **不解绑**,首页显示"门店已被停用,无需重新扫码,请联系总部" |
| 限流 | `429` | 冷却 65 秒(原有行为) |
| 本店弹幕来源设为协议采集(`dycast`,0.5.4 起) | `/api/vision/text` 回 `200` + `{"accepted":0,"ignored":"source","danmaku_source":"dycast"}` | **不是失败**:识别列表标"未使用",首页提示"上传的弹幕不会被使用";采集照常运行 |
| 网络错误、超时、5xx、没有 `need_bind` 标记的 401(如反向代理返回) | — | **一律不当成令牌失效**,不动绑定 |

发现入口有两处:① 上传弹幕时收到上述响应(`FrameProcessor` → `CaptureService`);
② 首页每次回到前台调一次 `GET /api/me`(60 秒限频)探测令牌,覆盖"采集空闲、没有上传请求"的时段。

**这些状态码和字段名客户端已经依赖,服务端改动时请保持兼容**:`401/410 + need_bind`、`403 + store_disabled`。

> 2026-10-15 补充:`POST /api/vision/text` 的 `items[].content` 现在是客户端**合并换行、去掉"昵称:"前缀、并做过模糊去重**之后的内容
> (一条弹幕折成两行时合成一项;同一条弹幕在画面上停留期间只上传一次)。字段结构没变,服务端无需改动。

## 2. 需要服务端改动的事项

### S1(建议优先)设备记录区分类型,"换新手机"不要误撤销采集手机

> **2026-10-19 更新:云服务侧已部署上线,视觉 APP 0.5.3 已登记发布(不强制升级);真机端到端验证尚未完成**(契约 [04](../../ailive-brain/docs/契约/04-门店设备接口.md) 已补)。
> 与下面的建议相比有两处取舍:① **门店 APP 不用改**——不带 `kind` 一律按 `zhubo`;② 老版本视觉 APP(没带 `kind`)由服务端在它**第一次调用
> `/api/vision/*` 时自动标成 `vision`**,不需要重新扫码或人工标注。"换新手机"默认只撤销 `zhubo`,管理台弹窗里有"同时撤销采集手机"勾选。
> 部署:线上库启动时自动加 `kind` 列(带默认值,幂等),已于 2026-10-19 随云服务部署完成(部署前已备份;线上 23 台设备此时都是默认的 `zhubo`)。
> 在采集手机第一次上传之前它仍是 `zhubo`,**确认管理台"门店设备"里它显示为"采集手机"之前,不要点"换新手机"**。
- **现状**:`devices` 表(`core/devices.py` 的 `_SCHEMA`)没有设备类型字段;`DeviceStore.revoke_all(store_id)` 和
  `POST /admin/store/<sid>/replace-device` 按门店整体撤销,**会把这家店的视觉采集手机一起撤销**。
  管理台确认框(`static/admin.html` 的 `replaceDevice`)只写"撤销当前所有设备",没有提示这一点。
  这是本次问题的根源之一(播放手机换机 → 采集手机被连带撤销)。
- **建议**:
  1. `devices` 加 `kind TEXT DEFAULT 'zhubo'`(迁移时旧设备默认 `zhubo`;已绑定的旧视觉设备可按 `app_version`/`model` 或人工标注一次)。
  2. `POST /api/app/bind` 的 `device` 对象接收 `kind`(`zhubo` / `vision`),未知字段原样忽略,保证向前兼容。
  3. `revoke_all(store_id, kind=None)`;`replace-device` 增加参数 `kind`(默认只换 `zhubo`,管理台提供"同时撤销采集手机"的勾选)。
  4. `/admin/devices` 返回并展示 `kind`;管理台"门店设备"列表增加"类型"列。
- **客户端配合**(服务端先上线后再改,不会破坏兼容):视觉 APP 在 `Api.bind()` 的 `device` 里增加 `"kind":"vision"`;门店 APP 同理 `"kind":"zhubo"`。
- **影响面**:`ailive-cloud`(devices/server/admin.html + 测试)、门店 APP、视觉 APP。

### S2 视觉设备专用的轻量"令牌探测"接口
- **现状**:客户端用 `GET /api/me` 探测令牌。该接口 `rt()` → `fleet.runtime(store_id)`,**会唤醒/创建该门店的云端运行时**(闲置会被回收),
  对一台只做上传的采集手机来说多余;每次回前台一次,量不大但属于副作用。
- **建议**:新增 `GET /api/vision/ping`(或通用 `GET /api/app/ping`),只走鉴权闸门并 `devices.touch()`,不碰 `Fleet`,返回
  `{"ok": true, "store": "...", "store_name": "..."}`。令牌失效仍返回 `401 + need_bind`,门店停用 `403 + store_disabled`。
- **客户端配合**:把 `Api.me()` 改指向新接口(一行改动)。服务端上线前客户端继续用 `/api/me`,功能不受影响。

### S3 设备"自助解除绑定"接口

> **2026-10-19 更新:`POST /api/app/unbind` 云服务侧已部署上线,视觉 APP 0.5.3 已登记发布;真机上"解除绑定后管理台显示已撤销"尚未验证。** APP 尽力调用、失败不影响本机解绑(契约 04)。
- **现状**:客户端新增了"解除绑定"按钮,但只清本机登录信息,**服务端对应设备记录仍是有效状态**(孤儿设备:总部设备列表里还在,令牌也还能用,只是没人持有)。
- **建议**:新增 `POST /api/app/unbind`(设备令牌鉴权,把自己的 `revoked` 置 1,并 `hub.kick`)。
- **客户端配合**:"解除绑定"先尽力调用该接口(失败/断网时仍然本地解除),再清本机。

### S7 `ingest_local_ocr` 的去重改成模糊匹配(兜底)
- **现状**:`vision_ocr._is_repeated` 只认"归一化后完全相同"(去空白、首尾标点)。同一条弹幕在画面上停留时,每帧 OCR 的错字都不同,
  每个变体都被当成新弹幕触发一次提问(2026-10-15 真机截图:5 次采样 21 行,画面里实际约 8 条)。
- **客户端已做**:视觉 APP 在上传前按字符相似度(最长公共子序列比 ≥ 0.6,≤3 字的要 ≥ 0.8)对最近 60 秒内的弹幕去重,并合并换行。
  所以服务端不改也能解决上述问题;但**别的客户端版本、旧版 APK、以后别的来源**仍会遇到,建议服务端同样兜底。
- **建议**:`_is_repeated` 增加一层相似度判断(同 `app/.../DanmakuDeduper.kt` 的做法,可对照其单元测试里的样本),
  阈值保守(宁可多问一次,也不要把两条不同的弹幕当成一条;"白车贴车衣会发黄吗"与"黑车贴车衣容易有胶纹吗"相似度就有 0.5)。
- **相关,更值得做的小改动**:`ingest_local_ocr` 把"xx 来了""开播地:…""欢迎来到直播间…"这类系统提示也当成观众提问,
  真机录屏回放里它们占了上传量的约四成,且占用每分钟 12 条的回答额度。建议服务端识别并丢弃(或客户端直接不传,见 README 已知限制)。
- **2026-10-16 更新:系统文字丢弃、进场提示去名字、词表纠正、大模型纠错已由服务端实现**(ailive-cloud,已合并 `main`,决策见 ailive-brain
  ADR-0032;云服务侧 2026-10-19 起已部署上线)。四层各有独立开关、默认全关,**手机端不用改、不用升版本**;本条里"服务端也做模糊去重兜底"那一点**仍未做**(客户端已做)。
  本地端到端联调(本 APP 0.5.2 + 真实 ML Kit + 录屏帧,同一组帧):触发答问的视觉事件 50 → 17,进场提示被当提问 18 → 0,系统文字被当提问 7 → 0。

### S8 弹幕来源按店可选(ADR-0033)

> **2026-10-20:云服务侧与本 APP 0.5.4 于 2026-10-20 合并 `main`,云服务侧已于 2026-10-20 部署上线,本 APP 0.5.4 已登记发布(不强制升级);云服务有单测,未真机验证。**契约见 [04「弹幕来源」](../../ailive-brain/docs/契约/04-门店设备接口.md),决策见 ailive-brain ADR-0033。

- 每家店有"弹幕来源":`dycast`(协议采集)/ `vision`(视觉采集)/ `both`(两者都收,缺省 = 此前的行为)。店员在**助播 APP「我的」**里改,总部台也能改并可锁定;**本 APP 没有设置入口**。
- 云服务强制:来源为 `dycast` 时**不处理**视觉上传,回 `200` + `{"accepted":0,"events":[],"ignored":"source","danmaku_source":"dycast"}`;设备最后活跃时间照常刷新。
  用 200 而不是 4xx,是因为 0.5.3 及以前的 APP 不认识 `ignored`,当成上传失败会满屏"上传失败,这几行已丢弃"——那几个版本只是把它显示成"已上传",无害。
- 本 APP 0.5.4:回包带 `ignored:"source"`、或 `GET /api/me` 的 `danmaku_source` 为 `dycast` 时,首页提示一句,识别列表对应条目标"未使用"。**采集与上传节奏不变**(不因此停采集、不退避),
  所以来源改回去后下一次上传就恢复被使用;提示由回包 / 探测更新(`/api/me` 探测 60 秒限频,上传回包即时)。
- 来源为 `vision` 或 `both` 时 APP 行为与此前完全一致。

### S9 视觉误提问治理(ADR-0037,2026-10-22)

> **2026-10-22/23:云服务侧(ailive-cloud#10)与本 APP(#8,版本 0.5.6)已合入 main,云服务全套 876 项、本 APP 154 项单测通过。云服务是否已部署、0.5.6 是否已登记发版,以线上 `/api/app/version?app=vision` 与部署记录为准;未真机验证。**
> 版本号:0.5.5(code 10)是 2026-10-20 的摄像头权限引导,那一版当时记为未发布;昵称拆分晚于它,单独用 0.5.6(code 11),不与 0.5.5 共用版本号——同一个 versionCode 对应两份不同的包,会让已装了前一份的手机收不到更新。
> 起因:真实直播测试里"这个稍等主播为您详细解答"刷屏无上限、平台提示 / 进场变体 / 助播自己的文字被当成提问、昵称被计时器粘连。

- **手机端(0.5.6)**:`LineMerger` 先剥行首的计时器 / 计数 / 匿名昵称"抖音用户"(含被读错的分隔符),时间 / 比分里的冒号不当昵称分隔符,纯计时器行不上传。**手机端的改动只有这一处**。
- **云服务侧(手机端不用改,旧版也生效)**:固定话术限次(`scheduler.canned_*`,缺省 120 秒 / 每分钟 1 条,**缺省就开**)、系统文字规则扩充与同一套前缀剥离(随 `drop_system`)、新两层 `echo`(回声过滤)与 `relevance`(非业务闸门,缺省影子)。各层开关与灰度见云服务交接说明、契约 03 / 04。
- **`/api/vision/text` 响应新增** `echoed` / `shadowed` / `filtered` 三个计数字段(只加字段,旧 APP 忽略);事件可能带 `shadow: "relevance"`。
- **标定提示**:标定弹幕区时避开助播 APP、总部大屏和平台提示卡片——这次回声的根源就是摄像头拍到了它们。

### S10 视觉弹幕起始行判定与近似重复过滤(ADR-0038,2026-10-23)

> **2026-10-23:手机端 0.5.7(code 12)与云服务侧已合入各自仓库 `main`(云服务全套 927 项、本 APP 179 项通过);0.5.7 发布包已构建;未真机验证。**
> 起因:真机第二轮测试里昵称仍混进内容、两三条弹幕并成一条。昵称 `月岛出逃指南。` 后的冒号常被读成 `、` `,` 或丢掉,旧逻辑几乎只靠冒号判"新的一条";行距与"上一行写满"两条判据没有余地(新弹幕 0.75 倍行高正好等于阈值)。

- **手机端(0.5.7)**:`LineMerger` 起始行改多线索(冒号 / 进场与系统格式 / 计时器与匿名昵称前缀 / 行首读对过的昵称 / 明显右缩),续行要有"外缩"或"小间距"的正证据,落单短续行不上传,`MAX_GAP_RATIO` 0.75 → 0.6,新增 `NickMemory`;**上传格式不变**,云服务无需配合。
- **诊断记录(新)**:预览页新增开关与"导出诊断包";缺省关、最近 12 帧、15 分钟自动停、仅在内存里,导出时才写应用私有缓存并调起系统分享。**第一个会把直播画面落盘的功能**,由使用者手动导出、自行保管。需要 FileProvider(`${applicationId}.diag`)与 `res/xml/diag_paths.xml`。
- **云服务侧(手机端不用改,旧版也生效)**:`echo` 增加 `vision_window`(缺省 60 秒,0 = 不比)——近期同店视觉上传里已有的同一条(OCR 变体 / 折行残片)被丢弃;`drop_system` 规则补进场新格式(带地点 / 粉丝文字)、底部工具栏、评论区占位、浮窗、小部件;`relevance` 词表并入商品名,问句形态补 `是什`。详见 [ADR-0038](../../ailive-brain/docs/adr/0038-视觉弹幕起始行判定与近似重复过滤.md)。
- **未验证 / 要靠诊断包**:`OUTDENT_RATIO` 1.5、`MAX_GAP_RATIO` 0.6 等阈值来自截图目测,真实帧上的表现要看第一批诊断包;颜色线索(昵称 / 正文 / 平台提示)本版不用。

### S11 近似重复的"号码 / 换主语"与回答前复述问题(ADR-0039,2026-10-23)

> **2026-10-23:手机端 0.5.8(code 13)与云服务侧已合入各自仓库 `main`(云服务全套 951 项、本 APP 184 项通过);未部署、未发版、未真机验证。**
> 起因:真机反馈"介绍一下1号链接"与"介绍一下2号链接"这类只差一个编号的问题被当成重复忽略;以及视觉采集没有昵称、回答显得突兀。

- **手机端(0.5.8)**:`DanmakuDeduper.same` 在相似度判断前先看两条规则:号码不同(阿拉伯数字与 `X号` / `第X` 里的中文数字,较短一边的号码是较长一边的结尾时视为行首徽章数字)、换了主语(去掉共同头尾后各 2~5 字、长度相差 ≤ 1、一个相同的字都没有)都不算同一条;相似度阈值不变。**上传格式不变**
- **云服务侧(手机端不用改,旧版也生效)**:`echo_score` 的号码规则改用同一口径(新增中文数字),`vision_same` 增加换主语规则,前缀否决只在剩下两段各 ≥ 2 字时才否决;**回答前复述观众的问题**(`responder.question_lead`,缺省对视觉来源开,可按店关,见契约 03 / 04);**播放回执额外延迟**度量(设备健康灯文字,契约 04)
- **未验证**:真机上新规则的误伤率(多上传一次由云端"同一回答冷却"兜底);复述句现场的听感与时延。

### S12 视觉采集心跳(2026-10-26)

> **2026-10-26:手机端 0.5.9(code 14)与云服务侧已合入各自仓库 `main`;是否已部署 / 发版以线上登记为准;未真机验证。** 接口与判定规则以契约 [04「视觉采集心跳与"采集手机"健康灯」](../../ailive-brain/docs/契约/04-门店设备接口.md)为准。
> 起因:协议采集即将退役、视觉采集将成为唯一弹幕来源,而手机只在有新弹幕时才上传——"直播间安静"与"采集手机没电 / 断网 / 被碰歪 / 应用被关"在云端和门店页上看起来一样,弹幕灯 5 分钟没弹幕就报黄,真出事时说的是同一句话。

- **手机端(0.5.9)**:采集服务运行期间每 60 秒发一次 `POST /api/vision/heartbeat`(设备 token 鉴权),载荷只有数字与状态——`v`、`state`(`capturing` / `stopped`)、`app`(versionCode)、`battery`、`charging`、`net`、`camera`(`ok` / `stalled` / `no_permission`)、`frame_ago` / `ocr_ago` / `text_ago` / `upload_ok_ago`(相对秒数,从未发生为 `null`)、`upload_fail_streak`、`uptime`。**不发图片,不发弹幕文字。**
  读不到的电量 / 充电 / 网络字段省略(契约允许缺省),四个 `*_ago` 字段"从未发生"发显式 `null`。
- **节奏与错误处理**:服务起来约 5 秒后第一次;之后以回包 `interval` 为准(夹 30~300 秒,缺省 60);一般失败 60 → 120 → 300 秒退避、成功后恢复;**429 当作"这一次没发成"**(按一般失败退避);**404(老云服务没有接口)拉到 10 分钟一次**,不影响上传;`401/410 + need_bind` 与上传路径一样清绑定(保留标定)、停采集、告警,**心跳不重试**;`403 + store_disabled` 只记日志、不解绑、节奏不变。
  心跳在独立线程上发(单次调用 8 秒总超时),识别 / 上传线程卡住时照发。
- **停止采集**:店员点"停止采集"时尽力补发一次 `state="stopped"`;系统回收、相机权限被撤销(`captureWanted` 仍为真)与令牌失效 / 解除绑定都不发,云端按"失联"处理。
- **上传计数口径**(影响 `upload_ok_ago` / `upload_fail_streak`):`/api/vision/text` 回 200 就算成功(**含** `ignored:"source"`——上传是通的,只是云端没使用);429 既不算成功也不算失败;其余错误(网络、超时、5xx、401 / 403 等)算失败,下一次成功清零。
- **云服务侧(手机端不用等它)**:心跳刷新设备最后活跃时间并存进设备记录;弹幕灯、总部台设备行、门店页"采集手机"灯据此判定。没发过心跳的旧版 APP(0.5.8 及以前)不受影响,仍按旧逻辑。
- **对 S6 / 第 3 节的影响**:采集服务在运行时,被总部撤销的手机约 1 分钟内能经心跳发现,不必等下次上传或回到前台;采集服务没在跑时仍然要等回到前台探测。
- **未验证**:整条链路没有在真机 / 模拟器上跑过(云服务与手机端各自只有单测);"600 秒无文字"等阈值是云端的经验值,真机数据出来后再调;`camera=stalled` 的 45 秒与看门狗同一个数,是否在弱机型上误报要看真机。

### S13 上传与识别解耦(ADR-0041,2026-10-27)

> **2026-10-27:手机端 0.6.0(code 15)在本仓库 `kain/2026102603` 分支;云服务侧在 `ailive-cloud` 的 `kain/2026102603` 分支(全套 1071 项通过);契约 04 与 ADR-0041 在 `ailive-brain` 的 `kain/2026102603` 分支;三处均未合并 `main`、未部署、未发版、未真机验证。** 接口以契约 [04「`/api/vision/text` 的耗时预算、答问收件箱、重试与幂等」](../../ailive-brain/docs/契约/04-门店设备接口.md)为准,决策见 [ADR-0041](../../ailive-brain/docs/adr/0041-视觉上传与识别解耦.md)。
> 起因:手机识别线程同步上传(云端同步答问,最坏 30 秒),期间一帧不处理;收到 429 又停 65 秒;失败的弹幕只靠"下一帧它还在屏幕上"才重试,滚出屏幕就永久丢了。协议采集退役后视觉是唯一来源,这些盲区就是丢弹幕。

- **手机端(0.6.0)**:识别线程只把弹幕**入队**([`UploadQueue`](../app/src/main/java/com/luxofilms/vision/UploadQueue.kt)),专用上传线程([`UploadEngine`](../app/src/main/java/com/luxofilms/vision/UploadEngine.kt))一批一批发。条目最多留 45 秒、队列最多 200 条(满了丢最旧)、一批最多 25 条、同一时刻一个请求在途、两次请求开始至少隔 1 秒;**失败就按 2 / 4 / 8 / 15 秒退避、沿用同一个 `batch_id` 重发**,直到条目过期;**429 只按 `Retry-After` 延后上传、不再停识别**;整个请求 15 秒总超时。队列只在内存里。
- **请求 / 回包的变化**:`POST /api/vision/text` 请求体多一个可选 `batch_id`(字符串,≤ 64 字符,同一批重试沿用同一个;老云服务忽略它);回包多一个 `pending`(云端因答问收件箱排队 / 超过等待上限而还没出的条数;老云服务没有,手机端不读)。**手机端不读 `events`**,所以云端"最多等 1.5 秒、`events` 可能不全"对手机无影响。
- **回包归类**(手机端 [`ApiUploadSender`](../app/src/main/java/com/luxofilms/vision/ApiUploadSender.kt)):`200`(含 `replayed:true` / `inflight:true`、含 `ignored:"source"`)→ 成功,这一批出队;`429` → 留着,等 `Retry-After` 响应头(没有看响应体 `retry_after`,再没有 20 秒;夹在 2~65 秒),**不算失败**;`401 / 410 + need_bind` → 令牌失效,清空队列、统一善后、**只报一次**;**其余全部**(网络错误、超时、5xx、`403 + store_disabled`、没有 `need_bind` 的 401 / 403)→ 失败,退避重试、**不解绑**。
- **云服务侧(手机端不用等它,但"至少一次"靠它兜底)**:按门店的**答问收件箱**(串行、每店最多 50 条、排了 20 秒未处理就丢、请求最多等 1.5 秒)把"收到弹幕"与"答问(可能走 L3 大模型)"拆开;按设备的 **`batch_id` 幂等台账**(每设备 256 条、120 秒;同一 id 重放回 200 + 当时的摘要 + `replayed:true`,仍在处理中回 `inflight:true`,重放不计入限流);429 带 `Retry-After` 响应头与 `retry_after` 字段。`/api/sim` 与 `/ingest` 仍同步,不变。
- **语义变化**:"上传至多一次"变成"**至少一次**"——云端处理过但回包丢了的批次会被重发;有 `batch_id` 的新云服务 120 秒内去重,**老云服务不认识,可能同一条多答一次**(回声过滤与"同一回答冷却"兜底)。**先部署云服务,再发 0.6.0**;新云服务 + 老手机、老云服务 + 新手机都能用,没有"必须同时升级"。没有总开关,回滚 = 回滚云服务镜像 / 不升手机。
- **心跳不变**:载荷与 S12 完全一致;排队深度、丢弃数是否进心跳放第二期。`upload_ok_ago` / `upload_fail_streak` 的口径不变(200 含 ignored 算成功,429 既不成功也不失败)。注意:断网期间上传线程按 2 / 4 / 8 / 15 秒退避重试,`upload_fail_streak` 增长的节奏变了(以前是每有一条新弹幕一次);云端判"弹幕上传连续失败"的条件是 `upload_fail_streak ≥ 3` **且** 120 秒内没有成功(`vision_link.py`),后一条起主导作用,所以判定时机基本不变。条目 45 秒过期后上传线程不再发(队里没东西),streak 停在原值,上传一直不通时灯仍保持 warn。
- **未验证**:整条链路没在真机 / 模拟器上跑过(模拟器虚拟画面没有文字,产生不了上传),手机端与云服务各自只有单测;"盲区消失"的实际效果、60 秒抖动下的重发重复率、慢 L3 时收件箱的丢弃比例,都要真机与线上数据。

### S6(不建议做)撤销时主动推送给视觉 APP
需要给只有 HTTP 的采集手机新增长连接或轮询,成本高。客户端"上传 401 + 回前台探测"已能覆盖,暂不需要。

## 3. 仍然存在、与服务端相关的已知限制

- **采集空闲且 APP 一直在后台时,撤销要等下次上传或回到前台才会被发现**(没有推送,见 S6)。
- **客户端没法在 APP 内端到端验证"上传 401"这条链路**:模拟器虚拟摄像头画面无文字,不会触发上传;该路径靠判定逻辑的单元测试加代码走读保证,
  上线前建议用真机在测试门店撤销一次设备实测。
- 管理台"门店管理"里创建的测试门店、测试设备会出现在正式列表里,联调用完记得清理。

## 4. 联调检查清单(服务端改动后)

1. 同一家店绑定播放手机 + 采集手机,点"换新手机"只撤销播放手机(S1 上线后),采集手机继续上传。
2. 撤销采集手机后,APP 回到前台 → 跳绑定页并提示,标定保留,重新扫码后点"开始采集"即可恢复。
3. 门店被停用 → 采集 APP 只提示不解绑;恢复启用后提示自动消失。
4. 采集 APP"解除绑定" → 管理台设备列表里该设备同步消失/标记已撤销(S3 上线后)。
5. 弹幕来源(S8 上线后):助播 APP 把来源改成"协议采集" → 采集手机几秒内(上传回包即时)出现提示、识别列表标"未使用";改回"视觉采集"或"两者都收" → 提示在下一次上传后消失;
   总部锁定后助播 APP 里改不了,采集手机提示不受影响。
